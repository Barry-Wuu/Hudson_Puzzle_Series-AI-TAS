## 数据层规格

NitroFS 里只有四个题库和一个转换脚本：

| 文件 | 记录数 | 索引范围 |
|---|---|---|
| `quest/quest10x10.bin` | 50 | 0–49 |
| `quest/quest15x15.bin` | 100 | 0–99 |
| `quest/quest20x20.bin` | 100 | 0–99 |
| `quest/quest25x25.bin` | 50 | 0–49 |
| `quest/quest.bat` | — | 官方打包脚本，透露题库由 CSV 经 `ilconv.exe` 转出 |

合计 **300 题**。每题是一条 `ILQT` 记录：

| 偏移 | 长度 | 含义 |
|---|---|---|
| `0x00` | 4 | 魔数 `ILQT` |
| `0x04` | 2 | u16 版本 |
| `0x06` | 1 | u8 宽 `w` |
| `0x07` | 1 | u8 高 `h` |
| `0x08` | 4 | u32 记录总长 |
| `0x0C` | 7×4 | 7 个 u32 段指针：标题 / 尺寸标签 / 答案词 / **美术层** / 网格位图 / 线索块 A / 线索块 B |

字符串为 Shift-JIS。四段关键区的读法：

- **美术层**：每格 1 字节。`value & 0x80` 置位 = 该格涂黑，**这就是数织的黑格**；低 4 bit 是成品图案的配色号（0–9）。答案盘面由它直接读出，不依赖网格位图。
- **网格位图**：`h×w` 行优先，只是「已涂/未涂」的成品底图，与美术层同源。
- **线索块 A**：长 `h·⌈w/2⌉` = **列**线索，每条**自下而上**。
- **线索块 B**：长 `w·⌈h/2⌉` = **行**线索，每条**自右而左**。
- 空槽位既可能是 `0` 也可能是 `0xFF`，**两种都必须丢掉**（只滤 `0xFF` 会让每条线索多出一个 `[0]`，300 题全错）。

校验方式：对每一题、每一行每一列，把盘面的连续段展开成线索数组，与解出的线索逐段比对：

```
runs(row y)      == reversed(B[y])     # 行线索右→左存储
runs(col x)      == reversed(A[x])     # 列线索下→上存储
```

结果 **300/300 通过**，同时 `ink（黑格数）== 行线索和 == 列线索和` 也逐题成立。各尺寸的黑格数范围：10×10 `32–74`、15×15 `75–168`、20×20 `124–294`、25×25 `244–421`。

> 线索方向是这条路线上最容易翻车的地方：先按「行线索自上而下、列线索自左而右」去读，横竖只能对一头；试过 8 种转置/翻转组合，最终只有「A 块=列、自下而上；B 块=行、自右而左」能 300 题全对。

## 填充剂量实测

「剂量」= 每格一次触摸的 `(gap, hold, after)`，单位秒；一次 xdotool 调用里串完所有动作，`sleep` 内嵌，避免每格 fork 进程的开销。

| # | 题号 / 黑格数 | gap / hold / after | 每格 | 实测 | 正解横幅 | 结果 |
|---|---|---|---|---|---|---|
| 0 | No.1 / 48 | 0.08 / 0.06 / 0 | 140 ms | 6.70 s | ✓ | 通关（PLAY TIME `00:00:06`） |
| 1 | No.2 / 48 | 0.06 / 0.04 / 0.02 | 120 ms | 5.80 s | ✓ | 通关 |
| 2 | No.3 / 59 | 0.05 / 0.05 / 0.02 | 120 ms | 7.10 s | ✓ | 通关（`00:00:07`） |
| 3 | No.4 / 48 | 0.02 / 0.04 / 0.015 | 75 ms | 3.61 s | ✓ | 通关（`00:00:03`） |
| 4 | No.5 / 43 | 0.015 / 0.03 / 0.01 | 55 ms | 2.38 s | ✓ | 通关（`00:00:02`） |
| 5 | No.6 / 48 | 0.01 / 0.02 / 0.01 | 40 ms | 1.93 s | ✓ | 通关 |
| 6 | No.7 / 74 | 0.012 / 0.02 / 0.003 | 35 ms | 2.61 s | ✓ | 通关 |
| 7 | **No.8 / 64** | 0.010 / 0.017 / 0.005 | 32 ms | 2.07 s | ✗ | **9 格不符** |
| 8 | **No.8 / 64** | 0.008 / 0.018 / 0.002 | 28 ms | 1.81 s | ✗ | **22 格不符** |
| 9 | No.7 / 74 | 0.008 / 0.015 / 0.005 | 28 ms | 2.10 s | ✗ | 27 格不符 |
| 10 | **No.8 / 64** | 0.012 / 0.02 / 0.003 | 35 ms | 2.26 s | ✓ | 通关（同题复测） |

结论：

- **35 ms/格是稳定下限**。第 7、10 行是同一道 No.8：32 ms 丢 9 格不通关，35 ms 一次通透 —— 变量只有剂量。
- 28 ms/格 开始明显丢格（64 格里丢 22、74 格里丢 27，约 25%–30%）。
- 丢格是**随机丢单个触摸**，不是坐标错位：读回的盘面与答案逐格对得上、只是少几格，所以补救办法是「重开重跑」，不是「修坐标」。
- 物理机制：触摸采样跟着 60 fps 走，一次按下要保持 ≳1 帧（16.7 ms）才会被看到，而两次触摸之间还要留 ≳1 帧的抬起间隙；总时长压到 30 ms 以下就是在赌帧相位。
- 通关时间与墙钟一一对应（7.10 s → `00:00:07`、3.61 s → `00:00:03`、2.38 s → `00:00:02`），说明游戏计时是真实时间，**逐格点没有额外加速空间，只能靠压剂量**。

### 踩坑

- **底部按钮栏盖住第 10 行**：栏体从 `y≈357` 起，第 10 行格心 `y=352` 仍在栏上缘之上，可以点；但一旦算错行距把 `y` 推到 364 以上，落点就是 `中断/設定`，会直接弹出菜单把节奏打断（第一次整盘填充失败就是栽在这里）。
- **盘面不是「10 列 9 行」的滚动视口**：10 列 ×16 px 正好 160 px，`x 87–247` 全在屏内；之所以看着像被裁，是因为左边界紧贴行线索区、下边界紧贴按钮栏。
- **`正解` 横幅会盖住盘面**：通关后逐格比对必然全错（横幅像素差触发「已涂」），只能用横幅本身判定，别拿盘面 diff 当验收。
- **光标所在行/列会整条高亮成黄色**：空板自检/读盘时要避开或容忍这个染色（空板判据放宽到 `R>240, G>220, 100<B<240` 正好同时容纳米白与黄高亮）。
- **选关页分母会变**：1 通时显示 `001/010`，8 通时显示 `008/030`，未解锁格子显示 `？`；ROM 里每个尺寸的题数是固定的（50/100/100/50），UI 的解锁节奏与「分母」的对应关系还没摸完，别把 `030` 当成题目总数。

## validation 截图（300 关 + 認定）

### 各关 `lNNN_clear.png`：怎么定「刚涂满、还没变色」这一帧

数织通关的实机节奏是「逐格涂黑 → 最后一格落笔 → 立刻播放浸染/上色动画 → 正解」，中间**没有停顿**，
所以「涂满」这一帧只能靠盘面本身认。全屏亮度、近黑占比这类粗指标在这游戏上全部失效：片头是整屏暗红、
片尾是整屏淡出、上色后图案里还有大片深色。最终用的是**对着答案盘逐格解码**：

| 步 | 做法 |
|---|---|
| 逐格判色 | 格心 3×3 邻域取 `max(R,G,B)<115 且 R>G+8` = 涂黑。黑格是暗棕红 `(67,22,30)`、空格是米白 `(252,244,220)`，两者判据毫无重叠 |
| 逐帧比对 | 与 `puzzles.json` 的答案盘比：`ag` = 逐格一致率，`miss` = 该涂没涂的格数 |
| 定帧 | 取**最后一个 `ag==1.0` 连续段的第一帧**，即最后一格落笔的瞬间 |
| 为什么要「段首」 | 浸染先动空格底色、后动黑格本体。底色从 `(254,244,220)` 一路褪成 `(230,237,226)` → `(203,229,236)` → 蓝，这一段 `ag` 仍是 1.0（黑格还没变），取段尾会拿到已经褪色甚至泛蓝的画面 |
| 兜底 | 上色完成后图案里的深色格（棕发、黑衣）依旧算「涂黑」，个别题整盘黑格恰好全落在深色区，`ag` 会继续等于 1.0；故再按「空格中位色仍属米白系」筛段 —— 判据是 `R≥200、G≥150、B≥110、R−B≥10、R−G≤22`（够亮 / 暖调 / 不发黄）。只看 `R−B` 会被「图案主色是暖色」的题骗过：15×15 No.004 是橘鬃绿底的狮子，中位色落在橘色上，`R−B` 照样为正，于是挑到了已经上色的一帧 |
| 再兜底 | 极少数片子里「整盘全对」的第一帧就已经带上浸染的暖色（图案主色本身偏黄），没有米白帧可挑，此时退而取「离纯米白 `(250,243,215)` 最近」的那一帧，并在报告里标注 |
| 时间精度 | 先 10 fps 粗扫定位，再在 ±0.5 s 窗口内 30 fps 精扫取段首 —— 涂满与浸染有时只隔 1~2 帧（@30 fps） |

### 怎么复现

```bash
python3 extract_vol6_clear_shots.py        # 300 张，8 进程，约 12 分钟
python3 check_clear_shots.py               # 逐张回读校验，退出码非 0 表示有不一致
```

`check_clear_shots.py` 不信任提取时的中间量，三路独立复核落盘 PNG：

1. **逐格对答案**：按格心重新解码，与 `puzzles.json` 比 `缺格 / 多格`；
2. **底色**：空格中位色要够亮、暖调、不发黄（同上判据）；
3. **杂色扫描**：盘面矩形里强饱和的绿/蓝像素 >300 就说明图案色已经上来了 —— 这一路完全不依赖格心取色，
   专门抓「格心恰好都落在深色格上、`ag` 仍是 1.0」的漏网。

**当前 300/300 全部 `缺0 多0`、底色米白、杂色 <300**。

逐帧采样点见 `extract_clear_report.json`（每张的 `t` / `agree` / `missing` / `paper`）。

### 落盘压缩

与 Vol.9 数独2 同一口径：先砍回 **RGB565**（R/B 取 `>>3<<3`、G 取 `>>2<<2`，抹掉 H.264 yuv420p
色度子采样带进来的上万色噪声），再中位切压成 **256 色索引 PNG**（`optimize=True, compress_level=9`）。
全部 256×384、`P` 模式，单张 42–84 KB。
