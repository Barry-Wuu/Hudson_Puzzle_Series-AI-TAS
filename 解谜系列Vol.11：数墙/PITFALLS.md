## 第二战：填充管线打通（第 001 問 实测通关）

**2026-10-19 白天**：`むずかしい 第001問` 实机通关，游戏内计时 **00:04:56**，评级 ★★★★☆。
结论先行：**填格全程不需要任何 NDS 按键，只用触摸**——与 Vol.13 同一条路子。

### ★★★ 填格机制（本作最关键的发现）

**点格子 = 移动光标 + 涂黑（用当前笔刷），一步完成。**

- 不必先移动光标再涂；也不必找任何确认键。
- 实测 `tap(72,72)` → 光标落到 `(3,3)`，且该格中心像素同时由 246 变 49（已涂黑）。
- 右侧菜单笔刷默认选中「黑方块」（橙色框），所以点格即涂墙。
- 重复点**同一格**不会擦除（安全），擦除要按「消す」或切白方块笔刷。
- 由此，填充循环极简：`for 每个 wall=1 的格: tap(该格)`。

我之前误走的两条弯路（都不必再试）：
1. 用 `x` 键涂黑——能生效但**丢键率极高**（实测连续 7 次只成 1 次），且丢失会导致同一格反复切换；
2. 用方向键遍历 + 按键涂——方向键本身可靠，但**每格要 2 个动作**，比触摸慢一倍。

### ★★ 触摸坐标（推翻首夜含糊之处）

- 下屏触摸**无命中区偏移**，`屏幕 = (384+x, 384+y)`，即 `nds_y = 局部y − 192`，**1:1 精确命中**。
  （首夜记的「各页偏移 15/21/30px」是误判，根因是当时用了**瞬时 click**：`xdotool click 1`
  的按下时长不够，游戏收不到，落点其实是上一次的鼠标位置。改成
  `mousemove → sleep 0.04 → mousedown → sleep 0.06 → mouseup` 后偏移全消失。）
- 触摸对**大按钮**（标题/存档/难度/菜单项）与**盘面格子**都有效；
  唯一失败的是**选关页的小格子**（每格仅 ~19×13px），该页改用方向键 + `x` 进入更稳。

### ★★ 视口几何（像素级钉死）

| 项 | 值 |
|---|---|
| 格线竖线 | x = 16, 32, 48, … 176（pitch 16） |
| 格线横线 | y = 208, 224, 240, … 368（pitch 16） |
| 格 (r,c) 中心 | **(24+16c, 216+16r)**（截图为 256×384 双屏图，下屏 y192-383） |
| 可见范围 | **10 列 × 10 行**（左边界 x=16，右边界 x=192 被右菜单切断） |
| 视口偏移 | `(or, oc)`，全图坐标 = `(or+vr, oc+vc)` |

⚠️ 首夜记的「格心 (24+16c, 216+16r)」是对的，中途被 y=224 那条线误导过一次，**以本节为准**。

### ★ 滚动规律

- **D-pad 是「光标推边」**（2026-10-24 lvl71 实测，推翻首夜「每按一次方向键 = 全图坐标 ±1、滚动自动跟进」的旧模型）：
  按键先移橙色光标，光标顶到视口边缘才推视口；光标到边后继续按钳位不动。
- **触屏黄▶按住可右滚任意列**（~0.055s/列；单点会跳 1~2 列不可靠）；左滚无触屏控件，只能盲按 Left 钳位到 oc=0。
- 滑块饱和：`oc ∈ [0, 14]`、`or ∈ [0, 4]`（24−10 / 14−10）。
- **视口定位只信上屏红框**（`mode2_fast.rect_oc()/rect_or()`，与盘面涂没涂无关）；
  按盘面三态反解偏移的旧 `loc.py` 方案在脏盘上会猜错，已随旧管线删除。

### ★ 视口定位器（现打法：上屏红框反解）

`mode2_fast.rect_oc()`：读上屏小地图红色取景框左边 x 反解 `oc`，24×14 另可 `rect_or()` 反解 `or`。
红框 84×84px = 视口 10 格 + 两侧各 1 格边距（不是 10 格）：18×10 每列 11px（`x_left = 13 + 11·oc`）、
24×14 每列/行 7px（`x_left = 33 + 7·oc`、`y_top = 41 + 7·or`）。旧 `loc.py` 按盘面三态滑窗匹配的
方案（含线索加权）已废弃——修复/校验定位只许用红框，按已涂图案反解在脏盘上会猜错视口，
在错误列补点 → 制造非墙误涂（实测翻车根源）。

### 速度拆解与已做的优化

| 阶段 | 旧打法 | 现打法（`mode2_fast.py`） |
|---|---|---|
| 每格触摸 | 逐格单进程 `after=0.42s` | **单进程连发 0.10s/格**（宽盘 TAP_WIDE 0.12s/格） |
| 触摸进程数 | 每格 4 次 xdotool 调用 | **单进程批量**：一条 `xdotool` 连发整块所有点击 |
| 视口定位 | 每按 1 键就截图求解（loc.py 三态匹配，已删） | **上屏红框反解** `rect_oc`/`rect_or` + 光标推边/黄▶按住滚动 |
| 单关填充耗时 | 112s（24×14） | 67~80s（旧管线末期实测）；现打法 18×10 ~22-25s、24×14 60-85s（ふつう实测） |

关键实现：`ds.tap_batch(points)` 把整块的点合并成
`xdotool mousemove x1 y1 sleep .04 mousedown 1 sleep .06 mouseup 1 sleep .16 mousemove x2 y2 …`，
一次进程完成二十余次点击。⚠️ 但 Vol.13 §L 的教训仍适用：**`mousemove` 与 `mousedown` 之间
必须留 ~40ms**，合并进单条命令时这个 sleep 不能省，否则 press 会落在上一个坐标上。

### 关卡序号 ↔ rec（已实机确认）

`むずかしい 第00N問` 逐关对应 `puzzles['むずかしい'][N-1]`，十二关连续命中，
每关都用「解答判定」通过（比比对像素更硬的证据）。

### ★★★ 选关页导航（batch 错位的真因）

选关页是 **10 列网格**，方向键按网格走：

| 键 | 含义 |
|---|---|
| `Right` / `Left` | 同一行 ±1 关 |
| `Down` / `Up` | **换行，±10 关**（不是 ±1！） |

所以「从第 11 关按一次 Down」= 第 21 关，不是第 12 关。首夜的 `Down×3` 到「むずかしい」
是难度菜单（4 项竖排，步长 1），两处步长不同，**别把难度页的手感套到选关页**。

**错位是怎么发生的**：旧跑批器早先假设「完成画面返回后光标停在刚通关那关，Right 一次即下一关」。
在 1~10 关内成立；但一旦光标被别的操作带偏（比如在选关页误点一次），后续每关都会连环错位——
实测曾把第 011 問 打成第 005 問、把第 012 問 打成第 017 問。

**加固做法（已落地）**：
1. 进关后**立刻读上屏标题的「第 NNN 問」**（截图裁 `y0-30` 放大即可目视，或模板匹配）——
  这是唯一无歧义的判据；靠盘面线索指纹匹配**不够**，10×10 视口下多解严重
  （实测期望题 bad=33、邻题 bad=36，差值仅 3，会误报）。
2. 线索指纹因此只配做**粗筛**：只有优势 >5 才判为错位，差值小就照常填、由「解答判定」兜底。
3. 每关通关后**人工/脚本确认 `クリアした問題` 计数递增**（存档页可见 `N/80`）。

### ★★★ 进关时视口不保证在 (0,0)（第四战新坑）

连着打十几关后，**新进关卡的下屏视口会继承上一次的滚动位置**（实测起手 `or=4 oc=5`）。
旧填充器原先假设「刚进关 = 视口左上角」，于是六个块全部对错位置，`unfixed` 一片、
填充耗时从 70s 涨到 150~185s，判定直接失败（错格被标橙）。

**修法**：填充前先暴力归位——
```python
ds.press_n("Left", 24, 0.22)   # 横向按到饱和
ds.press_n("Up",   16, 0.22)   # 纵向按到饱和
```
`Left/Up` 在边界会饱和、多按无副作用，所以比「截图求解 offset」可靠得多。加上这两行后
六块重新全部 `or=0/4, oc=0/9/14`、`unfixed=0`。

### ★★ 进关失败时只能补按 `x`，绝不能再按方向键

`x` 偶尔被吞（转场未走完），此时光标**仍停在目标关**。若重试写成「再按一次 Right + x」，
就会跳到**下一关**，把 A 关的答案填到 B 关盘面上——实测整批报废、白跑 8 分钟。

**正确重试**：只补 `x`（可多等 0.5s），一旦 `cursor_box` 有值就继续。

### ★★★ 题量分阶段解锁（20 → 40 → …）

每个难度并非一开始就把题全放出来：**初始只开放前 20 关**，选关页 21 以后是 `?`（不可选）。
打完第 20 关会弹提示：

> `GREAT!!` / `レベル「むずかしい」で問題が増えました！`

确认后选关网格从 1-30 扩到 **1-40**。所以：

- 批量脚本若发现「光标走不到目标关 / 进了 `?` 格」，先确认该关是否已解锁，不要误判成按键丢失。
- 做进度判断时以选关页的 `クリアした問題 N/80` 为准，那是存档里的真实计数。

## 第五战：21~40 关（むずかしい 后半）——填充稳定性与识别驱动

**2026-10-19 傍晚**：续打 21~40。前 21 关的管线在过半后暴露出多个隐蔽故障，逐个钉死如下。

### ★★★ 填充铁律：每格只点一次，否则「越修越坏」

- **致命点：点「已实心」的格会把墙退化成「仮置き」小点（dark≈9）**，甚至擦除。于是重试越多、坏得越多，
  最终补丁不降反升、判定失败（橙格）。
- 现打法（连发 + 原地补漏）单关填充 18×10 ~22-25s、24×14 60-85s（ふつう实测）；旧逐格慢参数下单关 120~140s 已废除。
- 铁律：**每格全程只点一次；只对仍为纯白的墙格补点；分区互不重叠**（`fill_wide`/`fill_huge` 按视口切段），
  修复永远朝答案方向 toggle（墙白→点黑、非墙黑→点白），黑墙/白非墙绝不碰 → 单调收敛。

### ★★★ 盘面状态匹配定位不可靠 → 现打法用「进关线索校验 + 上屏红框」

- 旧 `loc.solve` 用「空/数字/黑」对 `clue`+`wall` 滑窗匹配求 `(or,oc)`：空盘时 85 个空格匹配会**稀释线索差异**，
  同一盘面出现多个 `bad` 相近的解，甚至把真偏移误判（如真 (0,0) 被读成 (2,12)）；脏盘上匹配还会偏向「已填区域」。
  该方案已随旧管线删除。
- 现打法两路定位，都不依赖盘面涂色状态：
  1. **进关校验**：对目标题号跑 `clue_match(idx)`（≥ tot-2 才算进对关）——只校验线索，不碰涂色；
  2. **视口偏移**：上屏红框反解 `rect_oc`/`rect_or`（18×10 每列 11px、24×14 每列/行 7px）。

### ★★★ 进关先 settle 再识别（否则抓到转场空指纹）

- 按 `x` 进关后立刻截图，常抓在转场瞬间（画面还是上一页），识别得到空/错指纹。
- 必须 `sleep ~1.3s` 后重抓，或连续两帧 `diff<5000` 判为稳定再识别。

### ★★★ 选关页推进必须慢速

- `Right(1.0) + x(4.5)` 才能稳定「右移一关 + 进入」；`Right(0.7/0.22)` 会吞键，表现为停在原关或 x 被吞。
- `x` 偶发被吞：进关失败时**只补 x（可重试 3~4 次，每次等 4.5s）**，绝不再补 Right。

### ★★★ 选关页最可靠的进关方式：双击格子（绕开方向键异常）

- 选关页方向键极不可靠：**`Left` 在该页基本不生效**；`Right` 到第 36 关后不再推进；返回/存档过场还会吞键。
  靠方向键 + `x` 反复漂移，是本次卡在 36 关的根因。
- **正解：直接双击关卡格子进关**（单击只选中、双击才进入）。
  - 网格几何（本地坐标）：`x = 20 + 24*((L-1)%10)`，`y = 280 + 16*((L-1)//10)`；点击时 `ds.tap(x, y-192)`。
  - 例：第 31 关 = (20, 328)，第 32 关 = (44, 328)，第 40 关 = (236, 328)。
  - 双击后 `~3s` 进关，配合「全局识别题号」即可确保进对关。
- 有了双击 + 全局识别，40 关连续推进零失败（7 关 1127s）。该跑批器已随旧管线删除；
  现打法 `mode2_fast` 用「tap 选格 + x 进关 + `clue_match` 校验」，导航范式相同。

### ★★★ 从盘面退出到选关页（此前一直没找到的通道）


- 盘面上**按 `Start`（`Return` 键）** → 弹出「オプション」暂停菜单；
- 菜单右上「**ギブアップ**」(触摸 `(205, 48)`) → 弹确认 → 按 `x`（A）确认 → 回选关页。
- 用途：误入已解/范围外关卡时干净退出，不必强行解一遍。重清该题后ギブアップ标记会消失。

### ★★ 进关视口继承滚动 → 必须带校验归位

- 连打多关后，新进关卡视口会继承上次滚动位置（如起手 `or=1`）；盲按若丢键会归位不足。
- 现打法 `mode2_fast.enter_level` 用**带校验的归位兜底**：`Left×16 + Up×8` 后读回红框
  `rect_oc`/`rect_or`，非 (0,0) 再来一轮；clue mismatch 时同样先归位再重校验。

### 本战结论：识别驱动是最稳的范式

填格本身在「题号正确 + 视图归位 + 慢速单点」下是 100% 可靠的。真正的脆弱点全在**导航**。
因此把管线改成**校验驱动**：进关 → settle → `clue_match(idx)` 校验进对关 → `mode2_fast` 连涂填充 →
完成页判定（orange/darkblue 双特征）→ 按题号归档。即使推进偶尔漂移，也只会「解到相邻关」
而**绝不会把 A 题答案填进 B 题盘面**。

# 第四夜追加（2026-10-23）：大题滚动提速 —— 虚拟箭头 vs 键盘连发

问题：むずかしい 24×14 / 36×20 大题要滚视口，旧管线的滚动用键盘 `press_n`（0.36~0.53s/键）
且批量会丢键。**下屏滚动条上其实有黄色虚拟箭头（▲▼◀▶），能否点它提速？**

## 结论：虚拟箭头**不能**提速；真正提速的是「键盘单进程连发」

### 虚拟箭头实测（むずかしい第1問，右条 (187,287) / 左条 (3,95)）

| 尝试 | 结果 |
|---|---|
| 逐击 `ds.tap`，`after=0.15` | ✅ 5/5 生效（0.26s/格，含 spawn 开销）——**唯一有效的用法** |
| 单进程连发 ×10（0.10s/格） | ❌ **0/10 全吞**（箭头有节流，<0.2s 的连点无效） |
| 按住 2.0s | ❌ delta=0，**不支持按住连滚** |
| 同一坐标在 oc≥5 时逐击 | ❌ 0/16 —— **箭头本体随视口滑动**，固定坐标只在特定 oc 命中 |
| 光标在视口外 | 疑似也影响生效（未完全隔离验证） |

综合：自动化需要「每步重新定位箭头 + ≥0.25s 步进」，折算 ≥0.4s/格，**无提速价值**。

### 键盘单进程连发（重磅：零丢键）

```
args += ["keydown", key, "sleep", "0.10", "keyup", key, "sleep", "0.12"]  # × N，一条 xdotool
```

| 实验 | 结果 |
|---|---|
| Right×12 | **12/12 生效**（其中 9 键用于移光标、视口滚 3） |
| Left×12 | 12/12，对称回滚 |
| Down×13 / Up×13 | d_or=4/13 —— **13 键全部生效**，只是行方向最大滚动只有 4（14−10），其余被边界截断 |
| 耗时 | **0.245s/键**（press_n 实测 0.53s/键） |

**旧坑「批量按键会被吞」的真因**：`press_n` 每键 spawn 两个 xdotool 进程（keydown、keyup 分离），
进程调度抖动导致 SDL 丢事件；**同一进程内连发 keydown/keyup 则零丢失**。

### 落地建议

- 滚动改**键盘单进程连发**（`key_burst()`：一条 xdotool 内 keydown/keyup 连发，零丢键）——已落地
  `mode2_fast`：宽盘横向用触屏黄▶按住横滚（`hold_scroll`，自带红框校验，~0.055s/列），
  左滚/纵滚盲按钳位 + 红框双轴校验；盲按数给足，覆盖光标绕行最坏情况。
- 长按/连发对**箭头**无效但对**键盘**有效，不要混用经验。
- 按盘面涂色反解视口（旧 `where()` / loc.py）每次全图匹配约 1~2s，脏盘上还会猜错，已废；
  现打法用上屏红框反解，O(1) 且与涂色无关。

（当夜复现脚本 `scroll_bench1/2/3.py` 已随旧管线删除；结论均已并入 `mode2_fast` 与 `MODE3_PROGRESS.md` §3.1。）
