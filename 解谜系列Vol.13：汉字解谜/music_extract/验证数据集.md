## 二、可信的定量证据：节拍周期（谱通量自相关）

对 60s 音频算谱通量，再对包络做自相关，取 0.25~2.5s 区间前 5 峰：

| 音频 | 周期峰（周期 / 归一化强度） |
|---|---|
| **rec_BGM00**（录音） | 0.998s(0.66) / 1.997s(0.61) / 1.509s(0.51) / 0.511s(0.48) / 0.743s(0.40) |
| **修复版渲染**（循环窗×8 + 音符时长不除 factor） | 1.997s(0.78) / 0.998s(0.65) / 1.509s(0.59) / 0.511s(0.56) / 0.743s(0.56) |
| 旧 bug 版渲染（循环窗未×8） | **0.998s(0.95) / 0.255s(0.93)** / 1.254s(0.92) / 1.997s(0.92) / 2.252s(0.92) |

两点结论：

1. **录音与渲染的周期集合一致**（0.998 / 1.997 / 1.509 / 0.511 / 0.743s），主拍 = 0.998s（60 BPM），与「BGM00 就是这首」相符。
2. **旧 bug 版多出一根 0.255s(0.93) 的强周期**，录音里没有——正是鼓循环窗被压缩 8 倍导致的过密鼓点。修复后该峰消失，前 5 峰的**排序与强度都贴近录音**。这是修复方向正确的独立证据。

## 三、不可用的指标（必须说明，避免误导）

`verify_dataset.py` 现在仍会输出「旋律相关性 / 最佳音高补偿 / 同调」，但**这三项当前没有判别力**：

- 对裁剪后的录音做 −12 ~ +12 半音全区间扫描，chroma 中位相似度是**平的**：
  最低 0.8811、最高 0.8818，差异仅在第 4 位小数。
- 因此脚本报出的「最佳补偿 −6.00 半音」只是撞到 ±6 扫描边界，不是真实移调量；
  「旋转 0 bin = 同调」也没有意义。
- 速度项的 `onset_peak_corr` 仅 **0.021**（零延迟相关 ≈ 0），也就是说“scale=1.000”是噪声里的最大值，不能当作速度一致的证据。

**结论**：`verify_dataset.py` 的旋律/音高部分需要重写（例如改为对 onset 序列做对齐后的逐拍匹配，而不是逐帧 chroma 中位数）才可用。在此之前，判断 BGM00 与录音是否同一首、节奏是否一致，请以第二节的节拍自相关为准。
